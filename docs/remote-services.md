# Reach a private service through the VPN

For controller-managed profiles, use the [vpnmodo service commands](design/007-service-access.md).
The guide below remains the standalone deployment workflow.

Keep the workstation SSH configuration in the consumer project. This example
works with either VPN backend after its VPN and application containers are
connected. All addresses and account names below are placeholders.

The connection path is:

```text
workstation SSH client
  -> SSH to the Linux VPN VM
  -> docker compose exec application nc PRIVATE_HOST 22
  -> application network namespace shared with the VPN
  -> private destination SSH server
```

The VM SSH login and private destination SSH login are separate. The
workstation holds the keys and verifies the SSH host keys for both. The
application container supplies the TCP connection through the VPN; it does not
need an SSH server, copied private keys or agent forwarding.

## Configure the VM and private destination

Copy [ssh_config.example](../examples/ssh_config.example) into the consumer
project as `vpn/ssh_config`, then replace its example values:

```sshconfig
Host vpn-host
    HostName 203.0.113.20
    User operator
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
    ConnectTimeout 10

Host example-vpn-jump
    HostName 192.0.2.10
    User example-user
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
    BatchMode yes
    ConnectTimeout 10
    ProxyCommand ssh -T -o BatchMode=yes -o ConnectTimeout=10 vpn-host sudo -n docker compose --env-file /dev/null -p vpn-example -f /srv/example-project/vpn/instances/example/compose.yaml exec -T application nc %h %p
```

| Value | Replace with |
| --- | --- |
| `203.0.113.20` | VPN VM's address reachable from the workstation |
| `operator` | SSH account on the VPN VM, permitted to run the Docker command through noninteractive sudo |
| `192.0.2.10` | Private SSH destination reached through the VPN |
| `example-user` | SSH account on that private destination |
| `IdentityFile` | Workstation key for each SSH login; the two keys can differ |
| `vpn-example` | Actual Compose project name for this instance |
| `/srv/example-project/vpn/instances/example/compose.yaml` | Resolved runtime manifest on the VM |

The runtime manifest is generated by Ansible provisioning or the launcher's
first `connect`. Use this instance file, rather than the reusable source
`containers/<backend>/compose.yaml`, which needs additional deployment settings.
`--env-file /dev/null` avoids loading a runtime `.env`; the resolved manifest
already contains those settings. `-p` selects the intended Compose project.

Add this line to the workstation's `~/.ssh/config`, before broad `Host *`
settings, using the actual absolute consumer-project path:

```sshconfig
Include /absolute/path/to/consumer-project/vpn/ssh_config
```

This makes `vpn-host` available to the nested SSH command in `ProxyCommand`.
Ansible inventory aliases alone do not configure OpenSSH. If you instead use
`ssh -F ...`, also give that config path to the nested SSH command; the outer
`-F` option is not inherited.

## Verify both hops

First confirm direct SSH access to the VM and establish its expected host key:

```sh
ssh vpn-host true
```

Start the VPN using your deployment's connection procedure. On the workstation,
verify authenticated access to the private destination:

```sh
ssh example-vpn-jump hostname
ssh example-vpn-jump
```

Check that the hostname matches the intended destination. If prompted for a
new private destination host key, verify it through your usual trusted source.
With `BatchMode yes`, the example requires that key to be trusted already; for
first-use verification, run `ssh -o BatchMode=no example-vpn-jump hostname`.

OpenSSH replaces `%h` with the destination `HostName` and `%p` with its SSH port
(default 22). `nc` runs in the application container, so the destination is
reached through the VPN. Both `-T` options keep the proxy stream free of
terminal control characters. The VM account's `sudo -n` must succeed without a
password prompt. The private SSH server still performs its normal destination
user authentication.

## Forward an HTTP service to the workstation

Suppose the private SSH destination also serves HTTP on its own
`127.0.0.1:8080`. From the workstation, keep this command running:

```sh
ssh -N -T -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18080:127.0.0.1:8080 example-vpn-jump
```

In another workstation terminal:

```sh
curl --fail http://127.0.0.1:18080/
```

Open that same URL in a browser to use the service. The listener binds only to
the workstation's loopback interface. Press Ctrl-C in the SSH terminal to close
it. The destination SSH server must permit TCP forwarding.

To reach a service on another private host, replace the forward's destination:

```sh
ssh -N -T -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18080:192.0.2.20:8080 example-vpn-jump
```

Here `192.0.2.20:8080` must be reachable **from the private SSH destination**.
The forwarding connection originates there; it is not opened by `nc` directly
from the VPN container. Choose a free local port for each service. A successful
local bind does not prove the remote service is healthy; verify it with its
normal client.

The same `example-vpn-jump` alias works with `scp` and `sftp`. For multiple
managed forwards, see the consumer-owned mapping example in
[services.json](../examples/services.json) and `scripts/vpn-services`.

See the official OpenSSH references for
[ProxyCommand](https://man.openbsd.org/ssh_config#ProxyCommand) and
[local forwarding](https://man.openbsd.org/ssh#L).
